# Draft: отдельные процессы тяжёлого рендеринга (18.11.2026)

**Статус: инженерный кандидат, не разрешение на деплой.** Код переносит наиболее затратные по RAM операции из долгоживущего процесса FastAPI в отдельные краткоживущие дочерние процессы:

- финальная сборка 4:3 и 9:16 SVG/PNG/JPEG/ZIP, в том числе гибридный PRO с фоновыми Images-вызовами;
- шесть превью трёх AI-концепций;
- два полноценных растровых OpenAI-постера вместе с ZIP;
- PDF/DOCX/XLSX разбор документов делит с ними один слот памяти.

Общий поток: сервер валидирует файлы и бриф → создаёт приватный staging-каталог в PROMO_DATA_DIR (0700) и JSON с безопасными ссылками на бинарные данные → запускает системным Python модуль app.render_worker → дочерний процесс создаёт файлы и JSON-результат → завершается (вся память Pillow/CairoSVG возвращается ОС) → сервер отдаёт ссылки на файлы.

**Секреты:** скрипт не применяет pickle, не выводит пользовательские файлы и ключи в stdout/stderr. Приватные PROMO_PASSWORD_HASH и PROMO_SESSION_SECRET не передаются через переменные окружения ребёнку. Однако это НЕ файловая ОС-песочница: дочерний процесс работает с теми же правами на каталог и получает OPENAI_API_KEY для платных изображений.

**Ограничения:** один общий Python semaphore гарантирует один тяжёлый дочерний процесс только при одном Uvicorn worker. На текущем Time4VPS должно остаться --workers 1, MemoryMax=800M; суммарный расход RAM родителя и ребёнка **всё ещё может** превысить лимит. PROMO_RENDER_TIMEOUT_SECONDS (по умолчанию 300; допустимо 30–900) — время выполнения задания целиком, включая 2 оплачиваемых запроса; таймаут/kill → 503 без автоматической повторной оплаты. Успешно сохранённые платные изображения могут быть повторно использованы по ранее реализованному частному кэшу при идентичном запросе до TTL. Перед изменением лимитов проверяйте личный бюджет OpenAI.

## Приёмка перед слиянием и выпуском

1. Изолированный CI на актуальном main: Python, JavaScript, браузер, Docker; никаких настоящих платных запросов.
2. В тестовой среде 58-МП JPEG и PNG с альфой: проверка, что /api/generate выдаёт один ZIP со всеми исходниками и точными слоями без затирания модели/логотипа.
3. На действующем Time4VPS **без параллельных задач** RegionalResearch выполнить отчёт memory_report.sh до и после **одной** бесплатной 4:3+9:16 генерации реального исходника, затем при отдельном решении — один платный AI-фон. Проверить системные события max, oom, oom_kill, MemoryPeak, статус всех служб.
4. Сверить результат в CorelDRAW и читаемость кириллицы. Ни при каких условиях не менять Caddy, RegionalResearch и общий MemoryMax без отдельного согласования.
5. Если хотя бы один экземпляр MemoryPeak достиг 800 MiB, увеличилось число oom/oom_kill или перезапустилась служба, **не объединять PR / откатить тестовую сборку**. Нужна дальнейшая оптимизация входных JPEG и потребления памяти.

На прежнем коде после одной генерации наблюдали MemoryCurrent≈666 MiB, MemoryPeak≈800 MiB и memory.events max=262; поздняя диагностика новой запущенной версии **в простое** показывала ~79 MiB. Эти измерения нельзя сравнивать как нагрузочный тест и нельзя использовать как доказательство того, что дочерний процесс безопасен.

Этот документ не заменяет [инструкцию по безопасному выпуску](TIME4VPS_RELEASE_2026-11-18.md): PR нельзя включать в production только потому, что он прошёл CI.
